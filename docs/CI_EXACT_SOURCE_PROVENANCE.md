# GoreeCloud UI — exact PR source revision in CI

GitHub Actions `pull_request` checks commonly run against a generated merge commit by default. This is useful to test merge compatibility but **not** a byte-exact source claim for a draft release-candidate branch. A real source discrepancy was observed in draft 1.0.0 candidate PR #97: the branch HEAD was `493811849a6295f37d0337866722187ec9a58f45` while the Node 22 offline package evidence recorded synthetic checkout `9634a689ff1132845c71d60ea20009ccd90f47fb`. Even though source/package checks passed, **that tarball digest is not evidence for the declared candidate branch SHA**.

Both `.github/workflows/ci.yml` checkouts now explicitly use `ref: ${{ github.event.pull_request.head.sha || github.sha }}`, preserving exact PR source head on pull-request events and exact pushed source SHA for `main`. The workflow remains read-only, SHA-pinned, with checkout credentials not persisted. PR mergeability must still be evaluated separately; source CI is not a proof that merging into main is conflict-free.

**Release rule:** compare per-runtime `qa/package-evidence.json.sourceSha` to the exact recorded candidate PR head commit, verify the three package tarball hashes and final browser artifact run match that revision, and regenerate all evidence after any candidate revision. Never reuse artifact hashes from a synthetic merge SHA or a previous alpha source for the exact 1.0.0 candidate. This is source provenance for tests, not a cryptographic signature, registry publication or independently attested reproducible build.

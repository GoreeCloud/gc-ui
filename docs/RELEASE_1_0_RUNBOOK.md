# GoreeCloud UI — Stable 1.0 candidate, release and rollback runbook

**Status:** Prepared procedure, **not executed**, 2026-11-13. Package `0.1.0-alpha.0` remains unreleased to npm in the verified repository record. Preparing a local tarball is not a release or consumer migration. The sole Stable target is the web-foundation API in [PUBLIC_API_BOUNDARY.md](PUBLIC_API_BOUNDARY.md); native components and app migrations remain deferred.

## 1. Candidate and no-publication safety

1. Begin from the latest verified `main` commit; identify the exact source SHA and review open issues, dependencies, package/export map and release scope. Use a **separate draft candidate PR**, not a direct main push, release tag, registry publication or production deploy. On the candidate PR, set the package version to **exactly `1.0.0`** for tarball testing; record `status: candidate-unverified` until all evidence gates pass. A local candidate archive is not a Stable release.
2. `npm run check` (Node tests, contracts, tokens/contrast), `npm run verify:package` (offline-installed package and archive digest), `npm run browser:smoke` and `node tests/packed-foundation-browser.mjs` must pass from the **same candidate commit**. The tracked Git worktree must be clean. Verify all four CI jobs at that exact commit, including the Node 20/22/24 package evidence JSON and Chromium screenshots. No test may be reported passed just because it was scheduled.
3. Review the verified candidate's visual screenshots at 1440, 390 and 320 CSS px and any relevant feature states. The currently validated browser is **CI headless Chromium on Ubuntu 24.04**; no Safari/Firefox/physical device support is implied. Confirm no mandatory brand hue/theme, independent per-app appearance, keyboard/contrast/solid fallback and functional honesty.
4. Audit exported source, license/provenance, packaged marks, privacy and security on **that** SHA. Resolve the official brand-assets license/trademark distribution question and enable/verify main branch protection & required checks, or record an explicit founder-authorized alternative risk decision. Do not mark a gate verified on outdated alpha evidence.
5. The `registry/release-plan.v1.json` eight mandatory gates must all be explicitly verified with exact-SHA evidence; no disabled/missing gate is accepted. The `npm run release:status` report is informational. `npm run release:verify` is fail-closed. The new npm `prepublishOnly` script invokes that verifier to reject accidental normal `npm publish` while the candidate remains unqualified. **This is defense-in-depth**, not a provider-enforced registry publish permission; `--ignore-scripts`, compromised credentials or out-of-band publishing can bypass scripts. No credentials should appear in the repository.
6. Capture immutable candidate SHA, release CI URLs, npm pack artifact digest (SHA-256 and SHA-512), manifest of package exports/files, Node/npm/browser versions, visual review, security/license decision, relevant issue state and rollback instructions in the release issue. CI artifacts expire in seven days, so durable storage must be configured separately before any actual release.

## 2. Promotion after every gate is truly satisfied

Only after verified acceptance and authorized owner release action: review a locked candidate SHA; merge via the enforced PR workflow; **rerun the full quality matrix on resulting `main` SHA**, since squashing changes the SHA; update evidence to that exact final SHA. Then use the repository's configured release/tag/signed-artifact workflow and publish the exact reviewed tarball to the intended registry if such access and signing are actually configured. Read back the tag, release notes, package registry metadata, integrity digest and installable consumer behavior. Do not treat a draft GitHub PR, `package.json` 1.0.0 version string or locally packed tarball as distribution.

**Important:** A self-referential Git SHA cannot be embedded in its own commit. Record exact final SHA, hashes and CI artifact IDs in an **external issue/release record**, not a made-up precommitted SHA in the same file. Do not add GitHub/npm release or deployment by assumption.

## 3. Upgrade and safe rollback

- **Unpublished candidate:** stop promotion and close/retain the candidate PR with its checks; no registry or consumer state to undo. Revert the candidate branch through a new PR if code leaked to main; do not force-push protected history. The last documented working baseline before this qualification is Git [`c235f9b5`](https://github.com/GoreeCloud/gc-ui/commit/c235f9b5e2577c440465de0d455372c363f4d01d) with [green four-job CI](https://github.com/GoreeCloud/gc-ui/actions/runs/43447990325). This is a **source rollback target**, not proof of a published `0.1.0-alpha.0` npm version.
- **Published version, if one exists later:** first stop further new adoptions, preserve evidence and communicate the known defect. Revert affected source changes by ordinary reviewed PR, validate a corrected patch release, and pin consuming products to a previously **actually verified and available** package digest/version or local archive. Never tell users to install an unverified historical npm version.
- **If registry publishing went wrong:** request authorized owner action to deprecate/withdraw affected package versions according to registry policies, document impact, and ship a fixed compatible patch where appropriate. Assume npm unpublish/overwrite may not be permitted; don't promise immediate deletion, credential recovery or signed rollback without verifying the provider.
- **Consumers:** separately test restoration of application behavior/data boundaries. This shared presentation library stores no private user database; the user-facing product still owns its backups, configuration, authentication and recovery.
